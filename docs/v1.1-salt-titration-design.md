## 1. 目的とscope

v1.1は、物質そのものの名称・表示情報と、その物質1 molを水溶液へ投入した後の分析組成を分離する。これにより、酸または塩基そのものだけでなく、酸塩基familyの特定speciesと固定ionを与える塩・完全電解質を、AnalyteとTitrantのどちらにも同じ仕組みで配置可能にする。

新規の正式対象物質は次の2物質であり、物質マスターは12物質から14物質になる。

| ID | 表示名 | canonical formula | v1.1での位置付け |
|---|---|---|---|
| `na2co3` | 炭酸ナトリウム | `Na2CO3` | carbonate familyの`CO3^2-`を初期speciesとする塩 |
| `nahco3` | 炭酸水素ナトリウム | `NaHCO3` | carbonate familyの`HCO3-`を初期speciesとする両性の塩 |

主要acceptance scenarioはFixture H（Na2CO3 + HCl）の閉鎖系二段滴定曲線である。Fixture I（NaHCO3 + HCl）とFixture J（NaHCO3 + NaOH）も正式対象とする。

Na2CO3とNaOHのmixed analyteをHClで滴定するFuture Fixture Kは、将来拡張を妨げないarchitecture probeとしてのみ定義する。v1.1の入力、UI、solver fixture、acceptance test、Rendering scopeには含めない。

本versionでは、任意の反応式生成、沈殿、錯生成、活量補正、気液平衡、反応速度を扱う汎用reaction engineは作らない。登録済み酸塩基family、投入組成、固定ion、既存charge-balance solverをつなぐ最小拡張とする。

## 2. 確定原則

1. Na2CO3専用solverを作らない。
2. NaHCO3専用solverを作らない。
3. 物質名、formula、substance IDを比較する大量の条件分岐を作らない。
4. 既存のspecies distribution、mass balance、charge balance、log `[H+]` root findingを再利用する。
5. 既存のcarbonate familyとKa1/Ka2を再利用し、値・定義・出典を変更しない。
6. 物質ごとに初期family speciesを指定できる。
7. 物質ごとに固定ionと式量あたり化学量論数を指定できる。
8. 同じSubstance/composition modelをAnalyte側とTitrant側へ使用する。
9. 滴定方向を理由にsolverを分けない。
10. v1.0.0の既存12物質、Fixture A〜G、描画・export契約を変更しない。
11. CO2気相散逸、open-system carbonate、Henry則、gas phase、bubbling、kineticsを扱わない。
12. 当量点、特徴点およびsampling anchorのpHは、必ず対象体積で既存solverを実行して求める。

## 3. 物質と投入組成の分離

`Substance`は製品として選択する物質を表し、`DissolvedComposition`はその物質1 molを水溶液へ投入したときにchemical systemへ加える内容を表す。Na2CO3という物質をcarbonate familyそのものとして複製定義してはならない。

概念モデルは次を基準とする。実装時のreadonly指定やregistry APIの命名は調整できるが、意味を統合・省略してはならない。

```ts
interface InitialFamilyComponent {
  familyId: string;
  initialSpeciesId: string;
  stoichiometryPerFormulaUnit: number;
}

interface FixedIonComponent {
  speciesId: string;
  stoichiometryPerFormulaUnit: number;
}

interface DissolvedComposition {
  familyComponents: InitialFamilyComponent[];
  fixedIons: FixedIonComponent[];
}
```

- `familyId`は共有family registryを参照する。family定義を各塩へcopyしない。
- `initialSpeciesId`は、そのfamilyのどのプロトン化状態を1式量の開始状態とするかを示す。
- `stoichiometryPerFormulaUnit`は正のfinite値とする。v1.1対象では整数だが、型を整数専用にして将来の組成表現を妨げない。
- fixed ionは平衡分布させず、投入mol、係数、全液量から濃度を決める。
- 同一familyまたは同一fixed ionが両solutionから来る場合、family/species ID単位で物質量を合算してから希釈する。由来substance IDはdiagnostics用に複数保持してよい。
- `initialSpeciesId`は投入時の組成と中和経路の基準であり、平衡計算中にそのspeciesへ濃度を固定する指定ではない。平衡時にはfamily total全体を既存Kaで全speciesへ分配する。

## 4. Familyとfixed ionのregistry

現在の`AcidBaseFamily`へ安定した`id`を加え、共有registryから参照可能にする。v1.1では少なくとも既存炭酸系に`familyId: "carbonate"`を与える。既存species IDとstep IDは回帰リスクを避けるため維持する。

```text
family id: carbonate
species:   h2co3.h2co3 / h2co3.hco3 / h2co3.co3
steps:     h2co3.step1 / h2co3.step2
```

文書中の`H2CO3*`は、現在の実装が採用している見かけの炭酸speciesを意味する。canonical formula、species ID、Ka1、Ka2はv1.1で変更しない。

Na+のcanonical fixed-ion IDは`ion.na`に確定する。Phase 1で`src/chemistry/fixed-ions.ts`へ共有registryを置き、少なくとも`id: "ion.na"`、`formula: "Na+"`、`charge: +1`、`boundProtonCount: 0`を持つ定義を1件だけ登録する。Na2CO3とNaHCO3の`FixedIonComponent.speciesId`は必ずこのIDを参照する。

v1.1で共有registryへ移行する物質は新規のNa2CO3とNaHCO3だけとする。既存NaOHの`naoh.cation`を含むv1.0.0のcomplete-ion/species IDは移行しない。NaOHを`ion.na`へ単純置換してもpHは不変と予想できるが、`calculatePHDetailsAtVolume()`のdiagnosticsに現れるspecies IDまで変わり得るため、Phase 0ではデータ契約不変を優先する。KOH、Ca(OH)2、Ba(OH)2および既存酸の固定ionもv1.1では移行しない。既存物質のregistry統合は、全物質のcomposition migrationとdiagnostics契約を同時に扱う別Phaseまたは別versionへ延期する。

## 5. Substance modelの最小拡張

v1.1の目標形は、全Substanceが投入組成を持ち、酸塩基平衡定義と投入組成を別責務にする構造である。

```ts
interface Substance {
  id: string;
  displayNameJa: string;
  formula: string;
  /** @deprecated Pairing/equivalence decisions must not read this field. */
  roles: AcidBaseRole[];
  dissolvedComposition: DissolvedComposition;
  selectionCategory: "acid" | "base" | "salt-or-amphiprotic";
  acidBaseModel: SubstanceAcidBaseModel;
  provenance: SubstanceProvenance;
}
```

`selectionCategory`はUI表示用であり、組合せvalidationの根拠にしない。既存`roles: AcidBaseRole[]`はv1.1で**deprecated-but-retained**とし、後方互換のため削除しない。ただしpairing validation、proton-transfer direction、equivalence path、solver分岐の判断根拠として読むことを禁止する。capabilityは`initialSpeciesId`とfamily topology、および既存strong-hydroxide当量から導出する。コード上のdeprecated annotation追加はPhase 1以降の実装作業であり、本Phaseでは行わない。`roles`削除は、全物質のcomposition migration完了後の別Phaseまたは別versionでのみ検討する。

既存`protonation-family`と`strong-hydroxide`の平衡・強水酸化物モデルは破棄しない。`dissolvedComposition`は「何を投入するか」を担当し、既存modelはfamily定義、complete step、強水酸化物のOH-当量を担当する。強水酸化物をv1.1のためだけに水familyへ擬装しない。

既存12物質は次のlossless migrationとする。

- protonation-family物質は、実際に投入するformulaに対応するspeciesを`initialSpeciesId`にする。例: H2CO3は`h2co3.h2co3`、NH3は`nh3.nh3`。
- complete prefixを持つHCl/HNO3/H2SO4は、現在と同じcompiler規則でcomplete step後のfixed ionまたはactive familyへ変換する。
- NaOH/KOH/Ca(OH)2/Ba(OH)2は既存`strong-hydroxide`の`hydroxideStoichiometry`とcomplete ion情報を維持する。compositionへの段階移行時も、charge balanceへ入る固定陽ionとOH-当量を変えない。
- 移行前後のA〜Gについて、pH、当量体積、特徴点、全`CurvePoint[]`、SVG、PNGを回帰比較する。

## 6. Na2CO3 model

```ts
{
  id: "na2co3",
  displayNameJa: "炭酸ナトリウム",
  formula: "Na2CO3",
  roles: ["base"], // deprecated compatibility projection only
  selectionCategory: "salt-or-amphiprotic",
  dissolvedComposition: {
    familyComponents: [{
      familyId: "carbonate",
      initialSpeciesId: "h2co3.co3",
      stoichiometryPerFormulaUnit: 1,
    }],
    fixedIons: [{
      speciesId: "ion.na",
      stoichiometryPerFormulaUnit: 2,
    }],
  },
}
```

1 molのNa2CO3はcarbonate family totalを1 mol、初期species `CO3^2-`を1 mol、固定Na+を2 mol与える。初期speciesの電荷`-2`と固定ionの合計電荷`+2`が式量単位で中性になることをmaster integrity testで検証する。

プロトン移動profileは初期speciesから導出し、プロトン受容方向に2段階、供与方向に0段階である。HCl滴定時の順序は`CO3^2- -> HCO3- -> H2CO3*`であり、専用metadataや物質名分岐で2段を作らない。

## 7. NaHCO3 model

```ts
{
  id: "nahco3",
  displayNameJa: "炭酸水素ナトリウム",
  formula: "NaHCO3",
  roles: ["acid", "base"], // deprecated compatibility projection only
  selectionCategory: "salt-or-amphiprotic",
  dissolvedComposition: {
    familyComponents: [{
      familyId: "carbonate",
      initialSpeciesId: "h2co3.hco3",
      stoichiometryPerFormulaUnit: 1,
    }],
    fixedIons: [{
      speciesId: "ion.na",
      stoichiometryPerFormulaUnit: 1,
    }],
  },
}
```

1 molのNaHCO3はcarbonate family totalを1 mol、初期species `HCO3-`を1 mol、固定Na+を1 mol与える。初期speciesの電荷`-1`と固定ionの電荷`+1`が中性になる。

`HCO3-`からは`H2CO3*`へのプロトン受容1段階と、`CO3^2-`へのプロトン供与1段階が存在する。この両性はcompositionとfamily step位置から導出し、UI都合で単なる`base`へ固定しない。

## 8. Chemical systemへのcompile

composition compilerは単一`Substance`専用のentry pointへ固定しない。solutionを構成する1件以上の定量済みcomponentを受ける契約を基準とし、v1.1のsingle Analyte/Titrantは配列長1の特殊ケースとして渡す。UIの`TitrationInput`をv1.1で配列化する必要はない。

```ts
interface QuantifiedSolutionComponent {
  sourceComponentId: string;
  substanceId: string;
  amountMol: number;
}

interface CompiledSolutionComposition {
  totalVolumeL: number;
  familyAmounts: AggregatedFamilyAmount[];
  fixedIonAmounts: AggregatedFixedIonAmount[];
  protonTransferSources: ProtonTransferCapacitySource[];
}
```

```text
QuantifiedSolutionComponent[]
  -> each Substance.DissolvedCompositionをamount contributionへ展開
  -> family / fixed ion / proton-transfer sourceを集約
  -> CompiledSolutionComposition
  -> existing equilibrium solver
```

推奨責務分割は、単一componentを展開する`expandSubstanceComposition(...)`と、複数contributionを合算する`aggregateSolutionComposition(...)`、solver入力へ変換する`compileSolutionComposition(components, totalVolume)`である。公開・内部APIのいずれであっても、中心契約を`compileSubstance(substance, ...)`だけにしてはならない。

手順は次のとおりとする。

1. v1.1 UI境界で`n = concentration * solution volume`から各Substanceの投入molを求め、1要素の`QuantifiedSolutionComponent[]`へ正規化する。
2. 各componentの`familyComponent`について`amountMol * stoichiometryPerFormulaUnit`をfamily amount contributionへ展開する。
3. 各`fixedIon`について同様にfixed ion amount contributionへ展開する。
4. 既存strong-hydroxide modelの固定陽ionとプロトン受容capacityを、同じsource componentへ由来付けたcontributionとして保持する。
5. family ID単位、fixed ion ID単位で**物質量を**合算し、source componentの由来はdiagnostics用に保持する。
6. 合算後に全液量で割り、complete prefixの既存規則を適用してsolver用濃度へcompileする。
7. 既存species distributionでfamily totalを分配し、fixed ion、水のH+/OH-とともに既存charge balanceを評価する。
8. 既存root finderで`R(h)=0`を解く。

`CompiledSolutionComposition`はSubstance masterの別名ではなく、任意個の投入componentを集約したsolution-level valueである。mixed-analyte master、反応式engine、配列UIを導入しなくても、将来の`InitialSolution.components[]`から同じ集約境界へ接続できなければならない。

Na2CO3/NaHCO3の名前をcharge balanceへ渡す必要はない。Na2CO3ではNa+寄与が`+2 * n / V_total`、NaHCO3では`+1 * n / V_total`となり、carbonate species側の平均電荷とともに同じ残差式へ入る。

## 9. Mass balanceとinitial species

Na2CO3またはNaHCO3由来のcarbonate family totalは次である。

```text
n_carbonate = n_substance * 1
C_carbonate = n_carbonate / V_total
C_carbonate = [H2CO3*] + [HCO3-] + [CO3^2-]
```

`initialSpeciesId`の違いは、投入時の形式電荷、対ion、当量イベントの開始位置を決める。平衡後の濃度を`[CO3^2-] = C_carbonate`または`[HCO3-] = C_carbonate`へ固定するものではない。どちらも同一のKa1/Ka2と分布式を使う。

## 10. AcidBaseRoleとUI分類

酸塩基挙動は、ラベルではなく初期compositionから到達可能なプロトン化状態として扱う。

- `canDonateProtons`: 初期speciesより低プロトン化側へ1段以上進める、または既存の強酸供与当量を持つ。
- `canAcceptProtons`: 初期speciesより高プロトン化側へ1段以上進める、または強水酸化物の受容当量を持つ。
- Na2CO3: acceptのみ、2段階。
- NaHCO3: donate/accept双方、各1段階。

既存`AcidBaseRole = "acid" | "base"`と`Substance.roles`はv1.1で削除せず、deprecatedなcompatibility projectionとして保持する。新規物質ではNa2CO3を`["base"]`、NaHCO3を`["acid", "base"]`とするが、これは旧consumer向けの投影値にすぎない。validation、当量列挙、滴定方向決定が`roles.includes(...)`を使用することは禁止する。

UI selectは全14物質をAnalyte/Titrant双方へ1回ずつ列挙する。表示groupは`酸`、`塩基`、`塩・両性種`を使用し、Na2CO3とNaHCO3を最後のgroupへ置く。NaHCO3を酸groupと塩基groupへ重複表示しない。groupは見つけやすさだけを目的とし、選択可否や計算方向を決めない。

## 11. Pairing validation

`acid + base`というラベル比較を、compositionから作る`ProtonTransferProfile`の整合判定へ置き換える。profileは少なくとも、供与方向の到達step列、受容方向の到達step列、各方向の式量あたり最大当量を持つ。

候補方向は次の2つである。

1. Analyteが脱プロトン化し、Titrantがプロトンを受容する。
2. Analyteがプロトン化し、Titrantがプロトンを供与する。

proton-transfer candidate数に対する正式な3状態は次とする。

| candidate数 | 判定 | error code |
|---|---|---|
| 0 | incompatible pair | 既存`incompatible-acid-base-pair` |
| 1 | supported。必要なfamily/step/定数の確認後、その方向を使用 | なし |
| 2以上で一意に絞れない | ambiguous pair | `ambiguous-proton-transfer-direction` |

同一物質pairの既存`same-substance`判定はcandidate解決より先に維持する。既存`ValidationErrorCode`と`CalculationErrorCode`のruntime値はすべてlowercase kebab-caseで、`ValidationError.code`およびdiagnosticsへ文字列として露出する。このため、内部定数・symbol名とruntime code値を次のように分離する。

```ts
const AMBIGUOUS_PROTON_TRANSFER_DIRECTION =
  "ambiguous-proton-transfer-direction" as const;
```

- 内部定数名: `AMBIGUOUS_PROTON_TRANSFER_DIRECTION`
- `ValidationErrorCode`へ追加するruntime/diagnostics値: `ambiguous-proton-transfer-direction`

Phase 0で確定したcandidate 0/1/ambiguousの意味は変更しない。新codeはまだ実装・公開されていないため、この表現分離は既存diagnostics契約を破壊しない。uppercase文字列をruntime codeとして露出させたり、同じ意味のaliasを2件作ったりしない。

v1.1では完全な反応自発性・競争平衡判定engineを作らない。複数の独立reactive familyを含む物質、両側とも方向が曖昧な両性物質pair、沈殿等を伴うpairは安全側にunsupportedとする。UIで候補をdisableする場合も、Domainの同じresolver結果を使い、UI独自の物質ID表を作らない。

正式対応pairは少なくとも次を含む。

- Na2CO3 + HCl: Na2CO3側が2段階プロトン受容。
- NaHCO3 + HCl: NaHCO3側が1段階プロトン受容。
- NaHCO3 + NaOH: NaHCO3側が1段階プロトン供与。

これらは塩をTitrant側へ置いた逆配置でも同じcompiler/solverへ到達できなければならない。ただし当量イベントは「初期容器側の中和path」を基準に列挙するため、逆配置時のイベント数やcurveの見え方が正配置と同一であるとは限らない。

## 12. 当量点の一般化

現行の「Analyte familyの最もプロトン化された状態から`step.order`個」「Titrantの`protonCount`」という前提を廃止する。各solution componentは、初期speciesと決定済み滴定方向からcomponent-localなpath/capacity contributionを作れるが、最終的な当量点生成は単一pathを直接消費してはならない。solution全体のcontributionを反応stageごとに集約した`StoichiometricBoundaryPlan`を消費する。

```ts
interface StoichiometricCapacityContribution {
  sourceComponentId: string;
  processId: string;
  kind: "family-step" | "strong-hydroxide";
  equivalentMoles: number;
}

interface StoichiometricBoundaryStage {
  order: number;
  contributions: StoichiometricCapacityContribution[];
  incrementalEquivalentMoles: number;
  cumulativeEquivalentMoles: number;
  participatingStepIds: string[];
}

interface StoichiometricBoundaryPlan {
  direction: "protonation" | "deprotonation";
  stages: StoichiometricBoundaryStage[];
}
```

- family componentのprotonation方向では、初期speciesから高プロトン化側へ隣接stepを逆順にたどる。
- family componentのdeprotonation方向では、初期speciesから低プロトン化側へ隣接stepを順にたどる。
- componentの物質量と化学量論数を各capacity contributionへ反映する。
- strong-hydroxide capacityもfamily pathへ擬装せず、同じstageへ集約可能な別`kind`のcontributionとして表す。
- 一つのstageは複数source component/processのcontributionを持てる。boundaryと単一family stepを1対1に固定しない。
- stage順序・groupingは将来のmixed-system chemistry contractが決定する。v1.1は単一reactive componentから自明に得られるstageだけを生成し、任意混合物の順序判定engineは実装しない。
- Titrantの反対向き最大当量`q_titrant`をprofileから得る。
- stage `k`の体積は次で求める。

```text
V_eq,k = cumulativeEquivalentMoles_k / (C_titrant * q_titrant)
```

v1.1ではAnalyte componentが1件なので、`cumulativeEquivalentMoles = n_analyte * cumulativeAnalyteEquivalent`となり、既存式と同じ結果を得る。`EquivalencePoint[]`型と既存fieldを維持する。`order`は滴下体積順の1始まり、`stoichiometricEquivalent`は単一Analyte式量あたりの累積当量、`participatingStepIds`はそのstageまでに通過したfamily step IDとする。将来mixed analyteへ進む場合はsolution-level `cumulativeEquivalentMoles`および全process contribution metadataを追加し、単一物質用`stoichiometricEquivalent`へ混合量を無理に格納しない。絶対的な酸解離`step.order`をそのまま`EquivalencePoint.order`に流用しない。

Na2CO3 + HClでは次の2点となる。

| order | 変換 | step | 累積当量 |
|---|---|---|---|
| 1 | `CO3^2- -> HCO3-` | `h2co3.step2`の逆向き | 1 |
| 2 | `HCO3- -> H2CO3*` | 続いて`h2co3.step1`の逆向き | 2 |

当量点pHは各`volumeMl`で通常solverを実行する。近似値、中性固定、両性種公式を本計算経路へ入れない。

## 13. Characteristic Pointsの一般化

決定済み`EquivalencePoint[]`を体積昇順に並べ、`V_eq,0 = 0`として各区間の中点をhalf-equivalence characteristic pointとする。

```text
V_half,k = (V_eq,k-1 + V_eq,k) / 2
```

Na2CO3 + HClでは5.0 mLと15.0 mLの2点を生成する。各pHはその体積で既存solverを呼び、`pKa2`または`pKa1`を直接代入しない。`relatedEquivalencePointIds`は対応する後続当量点を少なくとも含み、IDと`order`は決定的にする。

## 14. Fixture H: Na2CO3 + HCl

```text
Analyte: 0.0500 mol/L Na2CO3, 20.0 mL
Titrant: 0.100 mol/L HCl
n(Na2CO3) = 1.00 mmol
```

必須期待値・不変条件:

- 第1当量点: 10.0 mL、`CO3^2- -> HCO3-`、`order = 1`。
- 第2当量点: 20.0 mL、`HCO3- -> H2CO3*`、`order = 2`。
- characteristic points: 5.0 mL、15.0 mL。
- 初期pHはfiniteかつ`> 7`。
- 全curve pointがfiniteで、数値許容差内で下降型である。
- `EquivalencePoint[]`に両点を保持する。

### 16.1 独立参照計算とpH tolerance

golden値は製品solver、`src/chemistry/species-distribution.ts`、`src/calculation/charge-balance.ts`、`src/calculation/root-finder.ts`のいずれもimportまたは呼出しせず、Phase 0用の一時的なPython標準`decimal`計算として得た。一時ファイルは作成していない。

使用した定数は既存25 ℃masterと同一の数値定義であり、`Ka1 = 10^-6.35`、`Ka2 = 10^-10.33`、`Kw = 1.0e-14`である。80 decimal digitsで、各体積の希釈後濃度、carbonate total、Na+、HCl由来Cl-またはNaOH由来Na+を明示して次を評価した。

```text
D = h^2 + Ka1 h + Ka1 Ka2
alpha(H2CO3*) = h^2 / D
alpha(HCO3-)  = Ka1 h / D
alpha(CO3^2-) = Ka1 Ka2 / D

R(h) = h + [Na+]
     - Kw/h - [Cl-]
     - C_carbonate * (alpha(HCO3-) + 2 alpha(CO3^2-))
```

`x = log10(h)`を`[-30, 6]`で500回bisectionし、全checkpointでmass-balance residualは`1e-80 mol/L`以下、charge-balance residualは`2e-80 mol/L`以下だった。さらに製品moduleをimportしない別のNode.js倍精度bisectionでも全checkpointが表示12桁まで一致することを確認した。出力は既存A〜Gと同じ10 decimal placesで保存する。

正式pH regression toleranceは既存A〜Gと同じ`toBeCloseTo(golden, 3)`とする。これは既存testが「`1e-3 pH`級」として採用している値であり、Vitestの判定上は`abs(actual - golden) < 5e-4 pH`に相当する。参照計算精度およびsolverの`1e-10` pH/log幅より十分緩く、表示丸めより十分厳しい。v1.1だけに新しい高精度toleranceを設けない。下降型などの別invariantに用いる局所比較toleranceはこのgolden regression toleranceと混同しない。

## 17. Future extension architecture probe: Fixture K

Future Fixture Kは次の非実装scenarioとする。

```text
InitialSolution components:
  - Na2CO3, amount = n_CO3
  - NaOH, amount = n_OH
Titrant:
  - HCl
```

component展開とcomposition集約後のsolution-level表現は、少なくとも次を同時に保持可能でなければならない。

- carbonate family total amount: `n_CO3`
- initial carbonate species: `CO3^2-`
- fixed Na+ amount: `2 n_CO3 + n_OH`
- NaOH由来strong-hydroxide proton-acceptance capacity: `n_OH`
- carbonate protonation capacity: 各段階`n_CO3`

OH-を固定濃度speciesとしてcarbonate familyと競合させない。既存strong-hydroxide表現から来る固定Na+をcharge balanceへ入れ、OH-濃度は他の系と同じく`Kw / [H+]`と電気的中性から求める。これにより、同じ`CompiledSolutionComposition`内でstrong hydroxide contributionとcarbonate familyを共存させられる。

HClに対するsolution-levelの累積stoichiometric boundaryは次である。

```text
stage 1 contributions:
  NaOH neutralization      = n_OH
  CO3^2- -> HCO3-          = n_CO3
boundary n1                = n_OH + n_CO3

stage 2 additional contribution:
  HCO3- -> H2CO3*          = n_CO3
boundary n2                = n_OH + 2 n_CO3
```

このprobeは、boundaryを単一`initialSpeciesId`のstep番号または単一Substanceの式量当量としてしか表せない設計を拒否する。`StoichiometricBoundaryStage.contributions`へNaOHとNa2CO3の両sourceを保持し、`cumulativeEquivalentMoles`をsolution-levelで集計できれば表現可能である。

ただし、stage 1へstrong-OH contributionと最初のcarbonate contributionをgroupingするchemistry resolver、mixed input型、濃度/体積UI、mixed fixtureのpH、sampling、Rendering/Export testはv1.1で実装しない。Fixture Kはacceptance fixtureではなく、architecture review/test-plan上の設計probeだけである。v1.1の正式acceptance scopeはFixtures H/I/Jのまま変更しない。

## 18. Adaptive SamplingとRendering

sampling algorithm自体の変更は原則不要である。一般化された`EquivalencePoint[]`と`CharacteristicPoint[]`を既存APIへ渡し、次を保証する。

- Fixture Hの10.0 mLと20.0 mLの両windowをrefinementする。
- 5.0、10.0、15.0、20.0 mLをexact anchorとして保持する。
- window重複やbase candidateとの近接時も、anchor優先でdeduplicateし、昇順・重複なしとする。
- sampling pointからpHを補間せず、全採用体積でsolverを実行する。

Rendering、SVG Export、PNG Exportは物質を解釈しないため、`TitrationResult`が正しく複数点を持てば既存経路をそのまま使用する。Fixture Hは既存の複数guide描画contractを実データで追加検証する。PNGはSVG由来とし、塩専用rendererを作らない。

## 20. Closed carbonate system契約

v1.1のcarbonate滴定は、全投入炭素がaqueous carbonate family内に保存される閉じた理論酸塩基平衡系である。`H2CO3*`は現在のfamily定義を維持する。

次は非対応である。

- CO2の気相への散逸、吸収
- 大気と平衡するopen system
- Henry定数、gas phase volume/pressure
- bubbling、攪拌速度、反応・物質移動kinetics

したがって、実験でCO2が脱離する条件の実測曲線との差をv1.1 solverの誤差として補正しない。実装・release完了後にREADME/Release Notesへこの前提を転記するが、本設計Phaseではそれらを変更しない。

## 22. 必須tests

### 22.1 Substance master / integrity

- 物質数が14で、`na2co3`と`nahco3`が存在する。
- ID、`displayNameJa`、canonical formula、UI categoryが正しい。
- Na2CO3は`carbonate` / `h2co3.co3` / family係数1 / Na+係数2。
- NaHCO3は`carbonate` / `h2co3.hco3` / family係数1 / Na+係数1。
- family/species/fixed-ion参照が存在し、係数が正のfinite値。
- 式量あたりの初期family speciesとfixed ionの電荷が中性。
- carbonate familyと既存Ka1/Ka2のobject/referenceまたは安定IDが再利用され、複製定数がない。
- invalid family ID、family外species ID、重複ID、不正係数、不正電荷を拒否する。

### 22.2 Compiler / solver

- Na2CO3 1 molからcarbonate total 1 mol、Na+ 2 molを生成する。
- NaHCO3 1 molからcarbonate total 1 mol、Na+ 1 molを生成する。
- Analyte由来とTitrant由来の同一family/fixed ionを正しく合算・希釈する。
- Na2CO3初期pHがfiniteかつbasic。
- NaHCO3初期pHがfinite。
- Fixtures H/I/Jの初期、各特徴点、各当量点、前後、過剰域がfiniteでcharge balanceを満たす。
- 3 pairの逆配置が同じcompiler/charge-balance/root-finderを通り、少なくともfiniteな対応結果または設計どおりの明示結果を返す。正式3 pairは物質がTitrant側であることだけを理由にunsupportedにしない。

### 22.3 Pairing / equivalence / characteristic

- Na2CO3のaccept profileが2段、NaHCO3のdonate/accept profileが各1段。
- Na2CO3 + HClがprotonation方向、NaHCO3 + HClがprotonation方向、NaHCO3 + NaOHがdeprotonation方向へ一意に解決される。
- candidate 0を`incompatible-acid-base-pair`、candidate 1をsupported、曖昧なcandidate 2以上をruntime code`ambiguous-proton-transfer-direction`として処理する。
- acid+acid、base+base、方向不定の両性pair、同一物質を明示的に拒否する。
- Fixture Hの当量点がexactに10.0/20.0 mL、order 1/2、関連stepがstep2/step1の順。
- Fixture I/Jの当量点がexactに10.0 mL。
- Fixture Hの特徴点が5.0/15.0 mL、Fixture I/Jが5.0 mL。
- 全当量点・特徴点pH calculatorが通常solver経路を呼ぶ。
- H/I/Jの全golden checkpointを`toBeCloseTo(golden, 3)`で検証する。

### 22.4 Sampling / curve

- Fixture Hの両当量点近傍がbase領域より高密度。
- 5/10/15/20 mL anchorがexactに含まれる。
- 全体積がfinite、厳密昇順、duplicateなし。
- Fixture Hは許容差内で下降型。
- Fixtures I/Jの全curve pointがfinite。
- max volumeを第1当量点後・第2当量点前へ指定しても、metadataには両当量点を保持し、範囲内だけsamplingする既存contractを維持する。

### 22.5 UI / Rendering / Export
