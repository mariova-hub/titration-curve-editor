# v1.2 mixed-analyte titration design

## 1. Status and authority

本書は、正式リリース済みのv1.1.0を基準に、v1.2で導入するmixed-analyte滴定の設計を定めるsingle source of truthである。本Phaseは設計のみを対象とし、production code、test code、package version、README、CHANGELOG、Release Notes、workflow、PWA、manifest、iconを変更しない。

v1.1の`v1.1-salt-titration-design.md`にあるFuture Fixture Kは、本書によってv1.2の正式acceptance fixtureへ昇格する。既存文書と競合するmixed-analyte事項は本書を優先し、v1.1 Fixtures H/J等の確定済み契約は変更しない。

## 2. v1.2正式scope

正式acceptance scopeは、共通体積の初期分析溶液にNa2CO3とNaOHが共存し、単一成分HClで滴定するFixture Kである。次をend-to-endで成立させる。

- mixed analyte inputとsolution-level正規化
- `QuantifiedSolutionComponent[]`によるcomposition aggregation
- 複数source/process contributionのstoichiometric stage grouping
- 2つの累積当量境界とcharacteristic point生成
- solution-level mass balance、fixed-ion charge balance、通常equilibrium solver
- 全当量点・特徴点をanchorとするadaptive sampling
- progressive disclosureによる2成分目のUI入力と組成summary
- 既存rendererによる2本のguide、Preview、SVG、SVG由来PNG

v1.2で正式に保証するmixed classは、次の全条件を満たすものに限定する。

1. 全分析componentがTitrantに対して同じproton-transfer方向へcapacityを提供する。
2. component間に初期の実質的なproton transferを必要とするdonor/acceptor対がない。
3. stage topologyが「1つのboundary-defining protonation-family pathと、0件以上のstrong-hydroxide prefix capacity」として一意に解決できる。
4. precipitation、complex formation、gas evolution等の追加processを必要としない。

Fixture Kはこのclassに含まれる。条件1と2だけを満たしても、複数family pathのstage alignmentを一意に証明できない場合はv1.2で推測せずunsupportedとする。domainは配列のまま維持するが、v1.2 UIとacceptance scopeを任意混合物editorへ拡張しない。

## 3. Mixed analyte input model

### 3.1 比較と決定

| 案 | 教員の入力体験 | v1.2判断 |
|---|---|---|
| A: 共通solution volume＋成分ごとの濃度 | 調製済み混合試料のラベルと一致し、単一分析物質UIから自然に拡張できる | **採用** |
| B: stock濃度＋stock volume | 調製操作には適するが、体積加成、希釈、混合後体積の説明が必要 | scope外 |
| C: amountMol直接入力 | 内部計算には明確だが、授業・実験で通常入力する濃度/体積から遠い | UIでは不採用 |
| D: substance＋concentration＋quantity/volumeの汎用配列 | 将来性はあるが、quantityの意味が行ごとに揺れ、汎用mixture editor化する | v1.2 UIでは不採用 |

UIは案Aを採用する。内部では案Aを曖昧さのない配列型へ正規化し、各行について`amountMol = concentrationMolL * totalVolumeL`を一度だけ計算する。stockを混ぜた履歴や、componentごとに異なるvolumeは保持しない。

```ts
interface AnalyteSolutionInput {
  totalVolumeMl: number;
  components: readonly AnalyteComponentInput[];
}

interface AnalyteComponentInput {
  componentId: string;       // UI行の安定ID。物質IDではない
  substanceId: string;
  concentrationMolL: number; // 混合後solution中の分析濃度
}

interface SolutionTitrationInput {
  analyteSolution: AnalyteSolutionInput;
  titrantSubstanceId: string;
  titrantConcentrationMolL: number;
}
```

既存`TitrationInput`はv1.0/v1.1 compatibility inputとして維持し、1成分の`SolutionTitrationInput`へ意味を変えず接続できるadapterを設ける。新旧fieldを同一objectで同時に許して優先順位を付ける設計は禁止し、判別可能なinput型または明示entry pointで正規化する。

### 3.2 UI上限とdomain能力

- UIは分析component 1件をdefaultとし、「分析物質を追加」で2件目だけを表示する。
- UI上限は2件、Titrantは従来どおり1件とする。
- 2件目は削除可能、1件目だけの通常操作では追加の概念を要求しない。
- domain/compilerの`components[]`に長さ2のhardcodeを置かない。2件制限はUI/validation policyであり、composition compilerの能力ではない。
- 行順は追加順を維持し、自動sortしない。順序は表示とerror focusの決定性だけに使い、化学計算結果へ影響させない。

### 3.3 UI表示

各行は物質selectと濃度入力を持ち、共通の「分析溶液の体積」は行の外に1つだけ置く。1件時の既存layoutとtab順を極力維持し、2件目追加時だけ行ラベルと削除buttonを現す。

計算前summaryは、たとえば次の形で表示する。

```text
分析溶液 20.0 mL
Na2CO3 0.0500 mol/L + NaOH 0.0250 mol/L
滴定液 HCl 0.100 mol/L
```

画面表示では既存formula formatterにより`Na₂CO₃`等の下付き表現を使う。errorは該当行/field直下と全体summaryの双方へ出し、重複時は後から追加・変更した行へfocusできるようにする。

## 4. Fixture Kの確定条件

案Aに基づき、Fixture Kを次で固定する。

```text
Analyte solution volume: 20.0 mL
  Na2CO3: 0.0500 mol/L  -> n_CO3 = 1.00 mmol
  NaOH:   0.0250 mol/L  -> n_OH  = 0.500 mmol
Titrant:
  HCl:    0.100 mol/L
```

NaOH量をcarbonate量の半分としたため、Fixture Hから第1/第2境界がともに5.0 mLだけ移動し、stage 1に両sourceが入ったことを明瞭に検証できる。

solution-level投入組成は次である。

- carbonate family total: `1.00 mmol`
- carbonate投入時species: `CO3^2-`
- fixed `ion.na`: `2 * 1.00 + 0.500 = 2.50 mmol`
- strong-hydroxide acceptance capacity: `0.500 mmol`
- carbonate acceptance capacity: 各family step `1.00 mmol`

`initialSpeciesId`はstoichiometric pathの開始位置を表すだけで、初期または滴定中の`[CO3^2-]`を固定しない。

## 5. NaOH composition participationとcanonical Na+

### 5.1 段階的adapterを採用する

v1.2ではNaOHの全面master migrationを行わず、**composition compiler入口の段階的adapter**を採用する。

- NaOHの既存`acidBaseModel.kind = "strong-hydroxide"`、`hydroxideStoichiometry = 1`、legacy `naoh.cation`/`naoh.oh`は削除しない。
- `DissolvedComposition`がないlegacy strong hydroxideを`QuantifiedSolutionComponent`としてcompileするとき、一般adapterがlegacy complete-ion metadataを読む。
- `kind = "fixed"`の陽ionはcanonical fixed-ion registryのalias resolverでcanonical IDへ変換する。v1.2で`naoh.cation`は`ion.na`へ解決する。
- `kind = "hydroxide"`はfixed ionへ変換しない。`hydroxideStoichiometry`から`StrongHydroxideProtonTransferCapacitySource`を1件だけ生成する。
- 明示`DissolvedComposition`とlegacy adapterの両方を同じcomponentへ適用しない。componentごとに展開経路を一意に選び、二重計上を防ぐ。

このadapterはNaOHというsubstance IDをboundary式やsolverで分岐するものではない。canonical registryが認識するlegacy fixed-ion aliasとstrong-hydroxide topologyに基づくmigration seamである。KOH/Ca(OH)2/Ba(OH)2のregistry migrationは本scopeへ暗黙に含めない。

### 5.2 diagnostics compatibility

既存single-analyte compatibility inputはv1.2中も現行legacy assemblyを使用でき、`calculatePHDetailsAtVolume()`に露出済みの`naoh.cation`を維持する。新しいmixed inputはcanonical compiled compositionを用い、`ion.na`とsource component IDsをdiagnosticsに出す。この差を同じinput shape内で不定にしない。

将来の全面migration時にはdiagnostics versioningまたはlegacy projectionを別途設計する。v1.2ではpH、mass/charge balance、当量、sampling、renderingの既存結果を優先し、全既存強水酸化物のdiagnostic IDを一括変更しない。

### 5.3 strong hydroxideの化学表現

NaOHからsolverへ固定投入するのはNa+の物質量だけである。OH-は次のいずれとしても保持しない。

- canonical/legacy fixed ion
- 初期固定濃度
- carbonate familyと競合する保存species

任意の滴下体積で`[OH-] = Kw / [H+]`とcharge balanceから求める。stoichiometry側の`n_OH`は、平衡濃度ではなくH+受容capacityの帳簿である。

## 6. Stage groupingの一般則

### 6.1 stageの意味

stageは「component-local pathの同じ配列index」ではなく、solution-levelで次のstoichiometric boundaryへ到達するまでに消費されるcapacity contributionの集合である。`order`は滴下体積順であり、acid dissociation stepの絶対`order`とは別物である。

単純な「各component-local pathのstep 1をstage 1へ入れる」規則は一般則として不十分である。異なるfamilyのlocal step 1は、強さ、開始protonation state、観測可能なboundary topologyが同じとは限らず、NaOH＋NH3等へ機械的に適用すると誤った境界を作り得る。

### 6.2 v1.2 grouping resolver

v1.2の正式groupable classに対し、次の順でplanを作る。

1. aggregate analyte profileと単一Titrant profileからproton-transfer方向を一意に決める。
2. 各sourceから由来付き`ComponentLocalStoichiometricPath`を作る。
3. 1つのprotonation-family pathをboundary-defining pathとして選ぶ。このpathの隣接family step列がstage 1..Nの骨格になる。
4. strong-hydroxide sourceはfamily stepへ擬装せず、protonation方向の**prefix capacity**としてstage 1へgroupする。strong hydroxideだけの単一分析物質なら自身が1 stageを作る。
5. family pathの各contributionを対応stageへ入れ、stageごとの`incrementalEquivalentMoles`を合算し、前stageから累積して`cumulativeEquivalentMoles`を作る。
6. 複数の非同一family path、逆方向source、または明示的alignment根拠のないpathが存在したら`unsupported-mixed-stage-grouping`とし、local indexで推測しない。

この規則は「Na2CO3ならこうする」というID分岐ではなく、family topologyとstrong-hydroxide process kindに基づく。将来複数familyを正式対応する際は、family間の`stageAlignmentKey`または熱力学的sequence resolverを別versionで追加する。

### 6.3 Fixture K boundary plan

```text
stage 1:
  NaOH strong-hydroxide prefix                   0.500 mmol
  CO3^2- -> HCO3-                                1.00 mmol
  incrementalEquivalentMoles                     1.50 mmol
  cumulativeEquivalentMoles                      1.50 mmol

stage 2:
  HCO3- -> H2CO3*                                 1.00 mmol
  incrementalEquivalentMoles                     1.00 mmol
  cumulativeEquivalentMoles                      2.50 mmol
```

したがって一般的な集約結果として、次が導出される。

```text
n1 = n_OH + n_CO3      = 1.50 mmol
n2 = n_OH + 2 n_CO3    = 2.50 mmol
V1 = n1 / 0.100 M      = 15.0 mL
V2 = n2 / 0.100 M      = 25.0 mL
```

この式、Fixture Kのsubstance pair、15.0/25.0 mLをproduction plannerへhardcodeしてはならない。

## 7. StoichiometricBoundaryPlan

現行`StoichiometricBoundaryPlan`は、各stageに複数`StoichiometricCapacityContribution`、source/process IDs、incremental/cumulative equivalent molesを既に保持するため、Fixture Kを表す型変更は不要である。v1.2で必要なのは、`createSingleReactiveComponentBoundaryPlan()`を置換する上記grouping policyである。

意味上の契約を次のように強化する。

- 同一`sourceComponentId`はstableで、UI行の順序変更で再採番しない。
- 各contributionはplan内でちょうど1 stageへ所属する。
- `incrementalEquivalentMoles`はstage contributionsの和である。
- `cumulativeEquivalentMoles[k]`は先頭からstage kまでのincremental値の和で、正かつ厳密増加する。
- `participatingStepIds`はfamily step用の累積compatibility projectionとし、全process traceは`contributions`を正とする。

mixed caseでは単一物質1 mol基準を定義できないため、`EquivalencePoint.stoichiometricEquivalent`へ混合比を押し込まない。mixed出力ではこのlegacy optional fieldを省略し、solution-levelの`cumulativeEquivalentMoles`と`participatingProcessIds`をoptional metadataとして`EquivalencePoint`へ投影する最小拡張を行う。既存consumerはvolume/order/IDをそのまま使用する。

## 8. Mixed analyte validation

validationはUI allowlistではなく、入力正規化、composition、capability、internal-reaction screening、stage groupingの順で行う。errorは決定的な順序で返す。

| 条件 | v1.2挙動 | 推奨code |
|---|---|---|
| component 0件またはUIで3件以上 | reject | `invalid-analyte-component-count` |
| 同じ`substanceId`を複数行へ入力 | 自動合算せず後続行をreject | `duplicate-analyte-substance` |
| 0、負、非finite濃度/換算amount | active行としてreject。不要行は削除する | `non-positive-number` / `non-finite-number` |
| unknown substance、composition未対応、未確認定数 | reject | 既存codeまたは`unsupported-analyte-component` |
| aggregate analyteとTitrantの方向が0件/複数 | reject | 既存`incompatible-acid-base-pair` / `ambiguous-proton-transfer-direction` |
| componentが決定方向へcapacityを持たない | reject | `incompatible-analyte-component` |
| analyte内にdonor/acceptor対がある | pre-equilibration対象としてreject | `pre-equilibration-required` |
| 同方向だがstage alignmentを証明できない | reject | `unsupported-mixed-stage-grouping` |

compilerが一般用途で0 amount contributionを無視できることと、UI/domain inputがactive componentの0濃度を受理することは別契約とする。v1.2 UIは0を「存在するが寄与しない成分」として保存しない。

### 8.1 pre-equilibration screening

各componentのinitial topologyからdonate/accept capabilityを求め、component Aのdonate processとcomponent Bのaccept process、またはその逆が同時に存在する場合、その混合は初期proton redistributionを必要とする可能性がある。v1.2は反応進行度を計算するpre-equilibration engineを持たないため、明示的に検証済みの非反応classでない限り安全側にrejectする。

- Na2CO3 + NaOH: 両者ともHClに対するacceptance側で、相互donorがないため受理。
- HCl + NaOHをanalyte内で混合: internal neutralizationを要するためreject。
- NaHCO3 + NaOHをanalyte内で混合: HCO3-からOH-へのproton transferを考慮する必要があるためreject。
- 異なる弱酸/弱塩基familyの混合: 同方向に見えてもstage alignmentまたはpre-equilibrationの証明がなければreject。

rejectされた系を単なるcomponent sumとしてsolverへ流してはならない。将来対応は、初期元素/族total、fixed-ion inventory、proton inventoryを保存したpre-equilibration結果をstoichiometric plannerへ渡す独立設計を必要とする。

## 9. Equilibrium solver integration

Fixture K用solver、mixed-analyte用solver、second-equivalence用solverは作らない。各滴下体積で次の既存経路へ接続する。

```text
AnalyteSolutionInput
  -> QuantifiedSolutionComponent[]
  -> compiled analyte composition
  + single titrant contribution at added volume
  -> solution-level family totals and canonical fixed-ion totals
  -> existing species distribution
  -> existing mass balance and fixed-ion charge balance
  -> existing log[H+] root finder
```

Fixture Kでは任意の滴下体積`V`において、carbonate total amountは1.00 mmol、Na+ amountは2.50 mmol、HCl由来Cl- amountは`0.100 * V(L)`である。全液量で濃度化した後、carbonate familyを通常のKa1/Ka2分布へ解き、H+/OH-とともにcharge balanceを満たす。初期compositionと平衡species distributionを混同しない。

既存solver architectureで不足しているのは、multi-component input assembly、strong-hydroxideのcomposition adapter、stage groupingである。species distribution、mass balance、charge balance、root finderの数式変更は不要である。

## 10. Equivalence、characteristic points、sampling

### 10.1 characteristic points

既存一般則をそのまま適用する。`V_eq,0 = 0`として連続boundary区間の中点を作る。

```text
V_characteristic,1 = V1 / 2          = 7.5 mL
V_characteristic,2 = (V1 + V2) / 2   = 20.0 mL
```

pHは各volumeで通常solverを呼ぶ。pKaの直接代入、Henderson-Hasselbalch近似、当量点pHの専用公式は禁止する。

### 10.2 adaptive sampling

既存samplingは`EquivalencePoint[]`と`CharacteristicPoint[]`を物質非依存で処理するため、algorithm変更は原則不要である。Fixture Kで次をacceptanceする。

- exact anchors: 0.0、7.5、15.0、20.0、25.0 mL
- 15.0/25.0 mLの両windowを局所refinement
- 全volumeがfinite、厳密昇順、重複なし
- 採用した全volumeでsolverを実行し、pH補間をしない
- 現行auto-range規則では最終25.0 mLと10.0 mL spacingから31.25 mLを得て、過剰HCl域を含む

必要な変更は新input型をcurve calculationへ渡す接続だけであり、mixed専用candidate generatorを作らない。

## 11. Rendering、SVG、PNG

新rendererは不要である。既存rendererは物質やstage contributionを解釈せず、`TitrationResult`の配列を描画する。Fixture Kでは次を確認する。

- Previewに15.0/25.0 mLのequivalence guide/markerが2組ある。
- 7.5/20.0 mLのcharacteristic guide/markerを既存visibility規則で扱う。
- SVGのcurve pathがfiniteで、2本のequivalence guideを保持する。
- PNGは同じSVGから生成し、独立rendererを設けない。
- style、axis、preset、typography、figure size、export filename契約は変更しない。

## 12. Fixture K independent golden pH

本設計Phaseではproduction moduleをimportせず、25 ℃の既存定数`Ka1 = 10^-6.35`、`Ka2 = 10^-10.33`、`Kw = 1.0e-14`と、明示した物質量/電荷収支だけを用いた80桁decimal bisectionを実施した。参照式は次である。

```text
D = h^2 + Ka1 h + Ka1 Ka2
alpha(HCO3-)  = Ka1 h / D
alpha(CO3^2-) = Ka1 Ka2 / D

R(h) = h + [Na+]
     - Kw/h - [Cl-]
     - C_carbonate * (alpha(HCO3-) + 2 alpha(CO3^2-))
```

v1.2 design golden値は次である。

| HCl added (mL) | position | golden pH |
|---:|---|---:|
| 0.0 | initial | `12.4051254613` |
| 7.5 | first characteristic | `10.7703912981` |
| 15.0 | first equivalence | `8.3383516242` |
| 20.0 | second characteristic | `6.3498931144` |
| 25.0 | second equivalence | `4.0025793867` |

500回bisection後の各charge-balance residualは絶対値`1.1e-80 mol/L`以下だった。さらにproduction moduleをimportしない別のNode.js倍精度bisectionで全5点が表示12桁まで一致した。Phase 0ではこの値をproduction solverの出力から再生成せず、上記の独立手順とcross-check証跡を正式fixture metadataへ固定する。pH regression toleranceはFixtures H〜Jと同じ`toBeCloseTo(golden, 3)`とし、表示丸め値をtest oracleにしない。

## 13. Additional checks and regression contract

正式acceptance fixtureはKの1件で十分である。ただしstage groupingが偶然0.500 mmolへ依存しないことを示すため、implementation時のplanner unit/property testに次の非golden補助caseを加える。これらを新しいrelease fixtureへ昇格させない。

- low NaOH: 20.0 mL中0.0050 M NaOH（0.100 mmol）ならV1/V2 = 11.0/21.0 mL。
- high NaOH: 20.0 mL中0.0750 M NaOH（1.50 mmol）ならV1/V2 = 25.0/35.0 mL。

v1.0 Fixtures A〜Gとv1.1 Fixtures H〜Jは全件regression対象とする。少なくともpH、equivalence/characteristic volumesとIDs、sampling順序/重複なし、auto range、single-analyte UI、SVG、PNG、reverse direction、既存validation codeを不変とする。既存input shapeとsingle-analyte操作を削除してから互換shimで戻す進め方は禁止する。

## 14. v1.2 scope外

- 任意成分数のgeneral-purpose mixed-analyte UI
- 3成分以上のanalyte UI、mixed titrant、componentごとのstock volume
- 初期混合時に強い内部中和または未解決proton redistributionを起こす組合せ
- alignment根拠のない複数protonation familyのmixed stage planning
- precipitation、complex formation、gas evolution
- open carbonate system、CO2散逸、Henry則
- activity/ionic-strength補正、kinetics、温度可変
- 全legacy物質とdiagnostics IDのcanonical registry全面migration

## 15. Implementation phases

現在のcodebaseの責務境界に合わせ、実装は次の順とする。各Phase完了前に次Phaseのproduction変更を混在させない。

1. **Phase 0 — Fixture/contract freeze**: 本書のinput shape、Fixture K、境界、golden値を独立cross-checkし、error code、legacy diagnostics inventory、test toleranceを固定する。production変更なし。
2. **Phase 1 — Input domain and validation**: `SolutionTitrationInput`、legacy input adapter、component count/duplicate/zero/internal-reaction validationを追加する。solverやUIはまだ切り替えない。
3. **Phase 2 — NaOH composition adapter**: legacy strong-hydroxideからcanonical fixed ionとcapacity sourceを一度だけ生成し、`ion.na` aggregationとdiagnostics compatibilityを検証する。
4. **Phase 3 — Solution-level stage grouping**: boundary-defining family path＋strong-hydroxide prefix ruleを実装し、`StoichiometricBoundaryPlan`不変条件とK/low/high casesを検証する。
5. **Phase 4 — Solver/curve integration**: mixed analyteを既存composition compiler、species distribution、charge balance、root finder、equivalence/characteristic generationへ接続し、Fixture K goldenを通す。
6. **Phase 5 — Progressive mixed UI**: 2行上限、追加/削除、共通volume、summary、行別error、single-analyte defaultを実装する。
7. **Phase 6 — Sampling/render/export acceptance**: exact anchors、両当量近傍、auto range、2 guide、Preview/SVG/PNG一貫性を確認する。algorithm/renderer変更は不合格時の最小修正だけとする。
8. **Phase 7 — Full regression/release preparation**: A〜K、reverse direction、UI/export全regressionを実行し、その後に限りversion/README/CHANGELOG/Release Notes等を別作業として扱う。

## 16. Risks and mitigations

| risk | failure | mitigation / acceptance evidence |
|---|---|---|
| stage groupingの誤り | OH-only境界や誤ったstep同居 | local index ruleを禁止し、family carrier＋prefix rule、plan invariants、low/high testを使用 |
| legacy/canonical Na+二重計上 | pHとcharge balanceがずれる | componentごとに展開経路を一意選択し、KのNa+ total 2.50 mmolをassert |
| OH-をfixed concentration化 | 初期/滴定中pHが物理的に不正 | fixed registryへOH-を登録せず、Kw/charge balanceだけで評価 |
| initial/equilibrium species混同 | CO3^2-を全量固定 | family totalだけを保存し、全volumeでspecies distributionを再計算 |
| UIの過剰一般化 | stock mixing/editor complexityが増える | 案A、共通volume、2件上限、単一Titrantに固定 |
| pre-equilibration系の誤受理 | component sumが初期化学を捏造 | donor/acceptor cross-screenと`pre-equilibration-required`でfail closed |
| duplicate component | amount/capacityの意図しない二重化 | 後続行をrejectし、自動mergeしない |
| single-analyte regression破壊 | 既存操作/API/diagnosticsが変わる | default 1行、legacy input path保持、A〜J全regression gate |
| Fixture K special case化 | 将来拡張不能 | substance ID/15/25 mL分岐を禁止し、process kind/topologyからplan生成 |
| internalsの2成分hardcode | 3件以上へ拡張不能 | UI policyだけ2件、compiler/planner inputはreadonly array |
| mixed metadataをlegacy equivalentへ押込む | 意味不明な値が公開される | mixedではlegacy fieldを省略し、moles/process metadataを使用 |
| error判定順の不定 | UI/testが不安定 | validation pipelineとrow orderを固定 |

## 17. Open items before implementation

化学scope、Fixture K input、boundary、UI上限、migration方針に未解決事項はない。実装開始前のPhase 0で、次の詳細だけを証跡付きで固定する。

1. 本Phaseでcross-check済みのgolden pHについて、独立計算の再現手順と定数sourceをfixture metadataへ残す。
2. v1.0/v1.1 testsが観測するlegacy diagnostics fields/IDsを棚卸しし、compatibility inputの厳密なprojection範囲を決める。
3. `SolutionTitrationInput`を既存関数の判別unionで受けるか、明示的な新entry pointで受けるかをAPI call-site inventory後に決める。両方式とも本書のcanonical input意味と旧input挙動は変えない。
4. 新validation codeの最終日本語messageとUI accessibility labelを既存命名規則に合わせて確定する。

これらはscopeを再選択する事項ではなく、Phase 0/1の実装契約詳細である。いずれかがA〜J regressionを維持できない場合は実装を進めず、本書を改訂する。

## 18. Design completion gate

本設計を実装着手可能と判断する条件は次である。

- 本書と既存3仕様書の参照関係が整合する。
- Fixture Kのinput、境界、characteristic volumes、golden値が一意である。
- NaOH/OH-/canonical Na+、stage grouping、pre-equilibration rejectionの責務が分離されている。
- sampling/renderer/exportsに専用実装が不要と確認されている。
- A〜J regression gateとscope外が明記されている。
- 設計文書以外に差分がなく、`git diff --check`が成功する。
